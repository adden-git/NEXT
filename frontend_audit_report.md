# NEXUS Station React Frontend — Security Audit Report

**Date:** 2026-05-06  
**Scope:** `/var/www/next/web/src/` — React SPA frontend  
**Auditor:** Senior Frontend Security Engineer  
**Methodology:** Static code review focused on XSS, CSRF, injection, file handling, memory leaks, race conditions, type safety, and secrets management.

---

## Executive Summary

The codebase is generally well-structured with good WebSocket isolation guards, request cancellation patterns, and XSS mitigations via `escapeHtmlOutsideCodeBlocks`. However, **several High and Critical issues exist** around token exposure in URLs, missing `noopener` on `window.open` calls, and insufficient path traversal sanitization. No hardcoded secrets were found, but the auth token is inadvertently leaked via download/upload URLs.

---

## Critical

### C1. Auth Token Leaked in File Download / Upload URLs
**Severity:** Critical  
**Files:**
- `web/src/hooks/useSessions.ts:639–644` (`getSessionFileUrl`)
- `web/src/hooks/useSessions.ts:652–657` (`getSessionFolderUrl`)
- `web/src/hooks/useSessionStream.ts:571–584` (`getSessionUploadUrl`)

The Bearer token is appended as a query parameter to file download and upload URLs:
```ts
const tokenParam = token ? `?token=${encodeURIComponent(token)}` : "";
return `${basePath}/api/sessions/${encodeURIComponent(sessionId)}/files/${encodeURIComponent(path)}${tokenParam}`;
```

**Impact:** Tokens are exposed in:
- Browser history and bookmarks
- Server access logs
- `Referer` headers when file contents contain navigable links
- Shared links if users copy/paste download URLs

**Fix:** Use `Authorization: Bearer` headers for file downloads (e.g., `fetch` + `Blob` + `URL.createObjectURL`) instead of token-in-URL. For direct `<a download>` links, implement cookie-based sessions or short-lived signed URLs.

---

### C2. `dangerouslySetInnerHTML` Used for Syntax Highlighting
**Severity:** Critical (mitigated by bundled-language whitelist)  
**File:** `web/src/components/ai-elements/code-block.tsx:416–419`, `:428–432`

```tsx
dangerouslySetInnerHTML={{ __html: html }}
```

The `html` is generated by Shiki (`codeToHtml`). While Shiki itself is a trusted syntax highlighter and the language is validated against `bundledLanguages` (line 238), any future vulnerability in Shiki’s grammar parsers or a compromised language grammar could lead to reflected XSS via assistant-generated code blocks.

**Fix:** Keep the bundled-language whitelist up to date. Consider running Shiki output through DOMPurify before injecting, or use Shiki’s `hast` / React-compatible output instead of raw HTML strings.

## High

### H1. `window.open` Without `noopener` on Blob URLs (Code Preview)
**Severity:** High  
**File:** `web/src/components/ai-elements/code-block.tsx:639–648`

```ts
const blob = new Blob([code], { type: "text/html" });
const url = URL.createObjectURL(blob);
window.open(url, "_blank");
```

The opened blob URL runs in the same origin and retains access to `window.opener`. Malicious HTML code injected by a compromised LLM or backend could manipulate the parent window (e.g., navigate it, extract data from `window.opener.location`).

**Fix:** Use `window.open(url, "_blank", "noopener,noreferrer")`.

---

### H2. `window.open` Without `noopener` on External Editor
**Severity:** High  
**File:** `web/src/components/session-settings-dialog.tsx:410`

```ts
window.open(`/files.html?path=${encodeURIComponent(fullPath)}&edit=1`, "_blank");
```

If `files.html` ever contains an XSS vulnerability, it can access and manipulate the NEXUS Station window via `window.opener`.

**Fix:** Add `"noopener,noreferrer"` as the third argument.

---

### H3. Insufficient Path Sanitization — Directory Traversal
**Severity:** High  
**Files:**
- `web/src/hooks/useSessions.ts:107–120` (`normalizeSessionPath`)
- `web/src/features/chat/components/session-files-panel.tsx:52–53` (`joinSessionPath`)

`normalizeSessionPath` strips leading `./` and `/` but **does not remove `../` sequences**. A path like `../../etc/passwd` remains intact and is passed to the API. While `encodeURIComponent` is used in URL construction, the backend decodes it. If the backend lacks strict path validation, this becomes a directory traversal vector.

**Fix:** Sanitize paths client-side by resolving `../` segments (e.g., using a path-normalization utility) and reject paths that escape the session root.

---

### H4. `workDir` Parameter from URL Passed Directly to API
**Severity:** High  
**File:** `web/src/App.tsx:192–193`

```ts
const workDir = params.get("workDir");
if (!workDir) return;
createSession(workDir).catch(() => {});
```

A crafted link (`?action=create-in-dir&workDir=../../../etc`) can trigger session creation in an arbitrary directory without client-side validation. The backend must validate, but client-side defense-in-depth is missing.

**Fix:** Validate `workDir` against an allow-list or normalize it with `normalizeSessionPath` (after fixing H3) before passing to `createSession`.

---

### H5. `window.open` Without `noopener` in Session Sidebar
**Severity:** High  
**Files:**
- `web/src/features/sessions/sessions.tsx:727`
- `web/src/features/sessions/sessions.tsx:979`
- `web/src/features/chat/components/chat-conversation.tsx:150`

These calls open same-origin URLs, but future changes that open external URLs would inherit the missing `noopener` pattern.

**Fix:** Consistently use `window.open(url, "_blank", "noopener,noreferrer")`.

## Medium

### M1. Error Messages Rendered Unfiltered in Toast Notifications
**Severity:** Medium  
**Files:** Multiple (e.g., `auth-page.tsx:63–64`, `useSessions.ts:183–185`, `settings-dialog.tsx:164–165`)

`catch (e: any)` blocks pass `e.message` directly into toast descriptions. While `sonner` renders text nodes (React escapes HTML), error messages that contain user-controlled or backend-controlled strings could still leak sensitive path information or be used for social engineering if the backend ever returns HTML in error details.

**Fix:** Sanitize or strip HTML-like tags from error messages before displaying. Use typed errors instead of `e: any`.

---

### M2. Auth Token Readable from URL Query Parameter
**Severity:** Medium  
**File:** `web/src/lib/auth.ts:41–49`, `:52–63`

```ts
export function consumeAuthTokenFromUrl(): string | null {
  const url = new URL(window.location.href);
  const token = url.searchParams.get(AUTH_TOKEN_PARAM);
  // ... stores token in localStorage
}
```

Users can be tricked into clicking a link containing a token, which then persists in their browser. If the link is malicious or logged, the token is compromised. `getAuthHeader()` also falls back to reading from the URL.

**Fix:** Remove the URL fallback from `getAuthHeader`. Only read the token from `localStorage` and require explicit user action (paste into a field) for URL-based tokens.

---

### M3. `catch (e: any)` Pattern Across Codebase
**Severity:** Medium  
**Files:** Widespread (e.g., `auth-page.tsx`, `settings-dialog.tsx`, `useSessions.ts`, `useSessionStream.ts`)

Using `any` for caught exceptions bypasses TypeScript safety. It allows accidental access to non-existent properties and makes it easier to pass unsanitized data into the UI.

**Fix:** Use `unknown` for caught exceptions and narrow with `e instanceof Error` before accessing `.message`.

---

### M4. Missing Content-Type Validation Before `response.json()`
**Severity:** Medium  
**File:** `web/src/hooks/useSessionStream.ts:2819`

```ts
const data = await res.json();
```

The `loadOlderMessages` fetch does not verify `Content-Type: application/json` before parsing. A compromised or misconfigured endpoint returning HTML/JS could cause JSON parse errors but not XSS directly. However, combined with other weaknesses, this reduces robustness.

**Fix:** Check `res.headers.get("content-type")` before calling `.json()`.

---

### M5. Unrevoked `URL.createObjectURL` in Preview Button
**Severity:** Medium  
**File:** `web/src/components/ai-elements/code-block.tsx:646–648`

```ts
window.open(url, "_blank");
setTimeout(() => URL.revokeObjectURL(url), 5000);
```

5 seconds may not be enough for the new tab to load and request the blob, leading to a broken preview or memory leak.

**Fix:** Revoke the object URL only after the page has loaded (e.g., via `window.open` reference or longer timeout) or serve the preview via a dedicated route.

---

### M6. `img` Tags Load External URLs Without Additional Validation
**Severity:** Medium  
**Files:**
- `web/src/features/tool/components/display-content.tsx:172–178`
- `web/src/features/tool/components/display-content.tsx:222–232`
- `web/src/components/ai-elements/message.tsx:534–540`

External image/video URLs from tool output or attachments are rendered directly. While `onError` handlers exist, a malicious URL could be used for tracking or to exploit image parser vulnerabilities in the browser.

**Fix:** Consider proxying external media through a trusted domain or implementing a strict URL allow-list.

---

### M7. WebSocket Reconnect Without Exponential Backoff
**Severity:** Medium  
**File:** `web/src/hooks/useSessionStream.ts:2789–2795`

```ts
reconnectTimeoutRef.current = window.setTimeout(() => {
  connect();
}, 100);
```

A 100ms fixed reconnect delay could lead to aggressive reconnection loops under network failure or server-side connection limits, potentially amplifying a DoS condition.

**Fix:** Implement exponential backoff with jitter (e.g., 100ms → 200ms → 400ms … max 30s).

## Low

### L1. `console.log` Statements May Leak Sensitive Data
**Severity:** Low  
**Files:** `web/src/App.tsx:291`, `web/src/hooks/useSessionStream.ts` (multiple lines)

Session IDs, user inputs, and WebSocket messages are logged to the browser console. In production builds, console logs may still be visible to users or browser extensions.

**Fix:** Strip or disable `console.log` in production builds.

---

### L2. `prompt()` Used for User Input
**Severity:** Low  
**File:** `web/src/components/settings-dialog.tsx:530`

```ts
const name = prompt("Название провайдера:", "openrouter");
```

`window.prompt` is a poor UX pattern, blocks the main thread, and is vulnerable to UI spoofing via `alert()` fatigue attacks in some threat models.

**Fix:** Replace with an in-app modal/dialog for provider naming.

---

### L3. `localStorage` Token Storage
**Severity:** Low  
**File:** `web/src/lib/auth.ts:31–34`

Auth tokens are stored in `localStorage` (30-day expiry). Any XSS vulnerability in the app or a dependency would grant immediate access to the token. There is no `HttpOnly` / `Secure` alternative because this is a SPA.

**Mitigation:** This is an architectural trade-off. To improve security, use short-lived access tokens with refresh tokens, or move to cookie-based sessions with `HttpOnly; Secure; SameSite=Strict`.

---

### L4. `any` Type Assertions in API Layer
**Severity:** Low  
**File:** `web/src/lib/api/runtime.ts:290–299`

```ts
export type Json = any;
export type HTTPBody = Json | FormData | URLSearchParams;
```

Using `any` for JSON responses weakens the type safety boundary between the API and the UI.

**Fix:** Replace `any` with `unknown` and add runtime validation (e.g., Zod schemas) for critical API responses.

---

### L5. Missing `rel="noopener noreferrer"` on Telegram Link
**Severity:** Low  
**File:** `web/src/App.tsx:36`

```tsx
<a href="https://t.me/alpsstroy1" target="_blank" rel="noreferrer" ...>
```

Actually has `rel="noreferrer"` but is missing `noopener`. While `noreferrer` implies `noopener` in modern browsers, explicit `noopener noreferrer` is safer for legacy support.

**Fix:** Add `noopener` explicitly.

---

## Recommendations (Priority Order)

1. **Remove token from query parameters** (C1). Use header-based auth for all API calls, including file downloads.
2. **Add `noopener,noreferrer`** to all `window.open` calls (H1, H2, H5).
3. **Sanitize file paths** to reject or normalize `../` segments before sending to the API (H3).
4. **Validate `workDir`** from URL params before calling `createSession` (H4).
5. **Replace `catch (e: any)`** with `catch (e: unknown)` and proper narrowing (M3).
6. **Implement exponential backoff** for WebSocket reconnects (M7).
7. **Strip production console logs** or guard them behind a debug flag (L1).
8. **Consider DOMPurify** for any future use of `dangerouslySetInnerHTML` (C2).
